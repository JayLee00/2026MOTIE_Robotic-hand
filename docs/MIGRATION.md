conda 환경 3종 내부(스크립트 shebang, `conda-meta`, editable finder 등 537개 파일)도 같은
규칙으로 보정했다.

**생성 URDF 스냅샷** — 경로 치환이 `urdf/generated/*.urdf` 의 "autogenerated by xacro from …"
주석까지 바꾸는 바람에 사이드카 `*.sha256` 해시가 어긋났고, 트윈 launch 가
`[urdf_snapshot] status='mismatch'` 로 기동 즉시 전체를 shutdown 했다.
`tools/urdf/regenerate.sh` 로 스냅샷+사이드카를 재생성해 해결했다.
재생성본과 원본의 차이는 **그 주석 한 줄뿐**임을 확인했다(로봇 형상 불변, 역치환 해시 대조로 검증).
place 사본도 동일하게 동기화했다.

**심볼릭 링크** — 텍스트 치환으로는 잡히지 않는 항목이 4개 있었다.
`franka_kistar_moveit_config/config/{ompl_planning,kinematics,fr3_controllers,fr3_ros_controllers}.yaml`
가 `/home/cy/fr_ws/src/franka_fr3_moveit_config/config/*` 를 가리키는 **절대 심볼릭 링크**였다
(그대로 두면 MoveIt 트윈이 kinematics/OMPL 설정을 못 읽는다). 두 워크스페이스가 모두
`tools/ros2/` 아래 있으므로 **상대경로 링크**로 다시 걸었다 — 프로젝트를 통째로 옮겨도 유지된다.
현재 트리에 깨진 링크는 0개다(HF 캐시 포함).

**남겨 둔 것** — 실행에 영향 없는 문자열:
`md_sja/*.md`(구 Docker/GWB 시절 메모), `docs/rate_log/*.log`(과거 실행 로그),
URDF 헤더의 "auto-generated from …" 출처 주석, `.claude/settings.local.json`,
`Topdown_Grasp_sja/data/**`(과거 실행 산출물 JSON), `configs/paths.yaml` 의
`__KISTAR_WS__`/`__MOUNT_MAP__`(구 Docker 경로 — 호스트 실행 경로에서는 미사용).

## 3. 구조 결정 (왜 이렇게 나눴나)

요청한 트리(`docs/`, `tools/{camera,RViz,MoveIt,URDF,env}`, `skill-set/*`)를 따르되
**한 가지를 바꿨다**: `camera` / `moveit` / `rviz` / `urdf` 는 실제로 모두 같은 colcon 패키지
(`franka_kistar_bringup`, `franka_kistar_description`, `franka_kistar_moveit_config`) 안에 있다.
이것을 넷으로 쪼개면 `package://` 참조와 colcon 빌드가 깨진다.

그래서:
- **워크스페이스는 통째로** `tools/ros2/` 에 둔다 (빌드 semantics 보존, `.git` 보존).
- `tools/{camera,moveit,rviz,urdf}/` 는 **진입점 디렉토리**로 만든다 —
  실행 래퍼(`check_camera.sh`, `launch_twin.sh`)와 "무엇이 어디 있는지" README 만 둔다.
  planner 가 서브시스템을 찾을 때 여기부터 보면 된다.

`skill-set/place` 는 `.git` 없이 이관되었다(번들에 포함 안 됨). 나머지 3개 skill 과
`dex_ros`, `fr_ws/src` 는 `.git` 이 살아 있다.

## 4. 상위 제어 계층은 새로 썼다

산업부 PC 에는 자연어 명령을 VLM 으로 파싱해 작업 종류를 고르고 FSM 으로 skill 을 돌리는
상위 계층이 있었지만 미완성이었다 — 내려놓기(seq 4)가 통합되지 않아 특정 과일 지목 명령이
place 없는 경로로 우회 라우팅되고 있었고, estop 도 배선되지 않은 상태였다.

통합하면서 그 계층은 가져오지 않고, **로봇을 실제로 움직이던 배선**
(`sequence_arbiter` 관측 + 단계별 프로그램 spawn)만 `pipeline/run_pipeline.py` 로 새로 썼다.
자연어 파싱 · 별도 지각 · 작업 종류 분기는 제외했다. 그 결과:

- 내려놓기가 4단계 체인의 정식 단계로 들어왔다(우회 라우팅 불필요).
- vLLM 서버 · GDINO · 전용 venv 의존이 사라졌다(시스템 python3 + PyYAML 만 필요).
- 상위 판단은 추후 VLM high-level planner 가 맡고, planner 는 `run_fruit_demo.sh` 를
  인자만 바꿔 호출하면 된다 ([ARCHITECTURE.md §6](ARCHITECTURE.md)).

시퀀스 규약(번호 배정 1/2/3/4, state 의미, 실패 회수)은 제어 PC 와의 계약이라 그대로 유지했고
[ARCHITECTURE.md §2](ARCHITECTURE.md) 에 정리했다.

## 5. 카메라 위치 변경의 영향 (리스크 해소)

Current PC 번들의 최우선 리스크는 **"카메라가 New PC 로 옮겨지므로 외부 캘리브레이션
(`core/extrinsic.py` / `tf.txt`) 이 무효"** 였다.

**카메라 발행자를 Control PC 로 확정하면서 이 전제가 바뀌었다.** 카메라를 물리적으로
옮기지 않았다면 `T(right_fr3_link0 ← front_cam_optical)` 은 그대로 유효하다.
따라서 이 항목은 **HARD BLOCKER → 확인 항목**으로 내려간다.

- 카메라·로봇 배치를 건드리지 않았다면: 그대로 사용, 첫 파지/배치에서 오프셋만 눈으로 확인.
- 배치를 건드렸다면: **파지·내려놓기 두 곳을 함께** 갱신해야 한다.
  - `skill-set/grasp/configs/calibration/extrinsic_20260612_170053.json`
  - `skill-set/place/vision_pipeline/core/extrinsic.py` (+ 참고 사본 `skill-set/place/tf.txt`)
  - bringup 의 static TF / URDF
