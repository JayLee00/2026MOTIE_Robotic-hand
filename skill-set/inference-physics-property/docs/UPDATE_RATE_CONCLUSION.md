> **대상**: `stiffness_deploy_ros2` (SHM 직접제어 → ROS2 토픽 배포 브리지)
> **측정일**: 2026-07-27 · **기준 데이터**: `docs/rate_log/20260727_010320_kiwi_contact/`
> 상세 절차·원본 로그는 [UPDATE_RATE_CHECK.md](UPDATE_RATE_CHECK.md), 배경은
> [TROUBLESHOOTING.md §F](TROUBLESHOOTING.md) 참고.

## 결론 한 줄

> **update rate 는 병목이 아니다.** 파이썬 루프 97.8Hz(학습 100Hz 정합), 촉각 센서 83.3Hz,
> 손 관절 199Hz — 모두 추론이 실제로 쓰는 **9.8Hz 를 크게 상회**한다.
> 남은 유일한 실질 문제는 **rate 가 아니라 힘의 크기**(임계의 45–52%)다.

---

## 1. 왜 측정했나

기존 가설(§F1~F2)은 *"파이썬 루프가 100Hz 를 못 채워(~20Hz) 추론 입력이 OOD 가 된다"* 였다.
이를 검증하려면 **무엇이 몇 Hz 로 도는지**를 수치로 확정해야 했다.

추가로, 측정 도중 **"`ros2 topic hz` 는 통신 속도이지 센서 갱신 속도가 아니다"** 는 문제가
드러나 계측 방식을 한 단계 보강했다(§2).

## 2. 핵심 개념 — "두 가지 rate" 를 구분해야 한다

| | 무엇을 재나 | 도구 | 한계 |
|---|---|---|---|
| **토픽 발행률** | 초당 메시지 수 (통신) | `ros2 topic hz` | 퍼블리셔가 **같은 값을 재발행**해도 정상으로 보인다 |
| **값 변화율** | payload 가 실제로 바뀌는 빈도 (센서) | `tools/sensor_update_rate.py` | **발행률을 넘을 수 없다**(상한이 곧 발행률) |

> 이 구분이 필요한 이유: `/paxini/right/ft` 는 **timestamp·seq 가 없는** `Float32MultiArray(12)`
> 라서, 프레임이 새 것인지 재발행인지 알 방법이 없다. 그래서 **값 변화로 역산**해야 한다.
> (SHM 에는 `Paxini_seq` 가 있지만 토픽으로 노출되지 않는다.)

**실제로 이 방식이 사고 하나를 잡아냈다** — `paxini_writer` 미실행 상태에서
`/paxini/*` 가 **0 을 89Hz 로 재발행**하고 있었다(`/ft` 12ch·`/raw` 1524ch 전부 정확히 0).
`ros2 topic hz`(89Hz 정상)·`attach()` 통과·`valid=1` 까지 전부 초록불인 **거짓 정상**이었고,
그 상태로 잰 힘 데이터는 전량 폐기했다. **이 '전 채널 0' 은 writer 미실행 탓이므로,
§F7 의 `ft` vs `Σ127` 판정에는 쓸 수 없다**(§7 참고).
(상세: [TROUBLESHOOTING §B1-b](TROUBLESHOOTING.md))

## 3. 신호별 결과

원 소스 rate 는 **제어 PC 코드**에서 확인한 값이고(이 워크스페이스에서는 직접 측정 불가 — §6),
발행률·값변화율은 이번에 실측한 값이다.

### 3.1 종합 비교표 — 토픽 발행률 vs 실제 데이터 변화율

| 신호 | ① 원 소스 rate | ② 토픽 발행률 | ③ 실측 값 변화율 | ②/① 관계 | ③/② 중복률 | 병목 |
|---|---|---|---|---|---|---|
| `/paxini/right/ft` (촉각 4×3) | **83.3Hz** (데이터시트, 12.0ms) | **89.9Hz** (`tactile_hz=90`) | **72.6Hz** (접촉 시) | 발행 > 소스 → **1.08배 과발행** | 19% (중복 7.4% + 양자화 ~13%) | ❌ 없음 (소스가 상한) |
| `/hand/right/joint_states` (16) | **1kHz** (EtherCAT) | **199.7Hz** (`arm_hz=200`) | **198.6Hz** | 발행 < 소스 → **5배 다운샘플** | 19.7% (정지 중 디더) | ⚠ **토픽이 병목** |
| `/franka/right/joint_states` (7) | **1kHz** (RT 토크 콜백) | **199.7Hz** (`arm_hz=200`) | (팔 고정 — 정지) | 발행 < 소스 → **5배 다운샘플** | — | ⚠ **토픽이 병목** |
| `/hand/right/kin` (12) | — (SHM 값 0) | **199.7Hz** | **0Hz (FROZEN)** | — | 100% | 소스 미동작 |
| `/hand/right/q_target` (발행측) | 루프 97.8Hz | 98Hz (중앙값) | — | 1:1 | — | ❌ 없음 |

**읽는 법**
- **③ < ②** 이면 소스가 발행률을 못 채우는 것 → 토픽은 병목이 아니고 **소스가 상한**이다(촉각).
- **③ ≈ ②** 이고 ① 이 더 크면 → **토픽 발행률이 상한**이다(관절 1kHz → 200Hz).
- ③ 은 원리적으로 ② 를 넘을 수 없다 → **③ 은 항상 하한값**으로 읽어야 한다(§6).

### 3.2 근거

- 촉각 83.3Hz: **센서 데이터시트**(12.0ms 주기). `tools/paxini_writer.py` 주석의 "~90Hz" 는
  개략치이며, 수신 루프는 **이벤트 구동**(고정 sleep 없음, 버스트 시 최신 프레임만 유지).
- 발행률: `shm_state_publisher_node.cpp` 의 **고정 wall timer** —
  `arm_hz=200.0`, `tactile_hz=90.0`. 데이터 도착과 무관하게 최신 SHM 스냅샷을 재발행한다.
- 관절 1kHz: `Dual_Arm_Hand_Ctrl/docs_dev/README.md` — `ecatthread` EtherCAT cyclic I/O
  **(1 kHz, Hand)**, Franka **1 kHz RT torque callback**.
- `/hand/right/kin` 은 통합모델이 `USE_JKIN=False` 로 **입력에 쓰지 않으므로 무해**
  ([real_deploy_inference_final.py:113](../stiffness_deploy_ros2/launch/real_deploy_inference_final.py#L113)).

## 4. 파이프라인 rate 여유 — 병목 없음

```
촉각 센서 83.3Hz ─┐
                  ├→ 파이썬 모션·샘플링 루프 97.8Hz ─→ FACTOR=10 다운샘플 ─→ 추론 입력 9.8Hz (15 steps)
손 관절 199Hz    ─┘                                                             ↑ 학습 스펙과 동일
```

| 단계 | 측정값 | 학습 스펙 | 판정 |
|---|---|---|---|
| 루프 유효 rate | **97.8Hz** (3회, 편차 0.1) | ~100Hz | ✅ 정합 |
| downsample steps | **15** | ≥ MIN_LEN(10) | ✅ 충분 |
| 촉각 센서 갱신 | **83.3Hz**(소스), 관측 72.6Hz, 전 12채널 반응 | ≫ 추론 9.8Hz | ✅ 여유 |
| setpoint 발행 (`q_target`) | 중앙값 **98Hz** | ~100Hz | ✅ 정합 |

> 촉각 83.3Hz 는 루프 97.8Hz 보다 **낮다**. 즉 루프는 매 tick 새 힘 값을 받지는 못하고
> 약 1.2 tick 마다 갱신된다. 다만 **추론이 쓰는 9.8Hz 의 8.5배**라 정보량은 충분하다
> (학습 데이터도 동일 센서·동일 SHM 경로로 수집됐으므로 이 조건 자체가 학습과 같다).

⇒ **이전 "루프 ~20Hz 병목" 가설은 반증됐다.** `FACTOR` 재조정도 불필요하다.

## 5. 주의 — "값 변화율"은 접촉력에 따라 달라진다

촉각 Fz 는 **0.1N 단위로 양자화**되어 있어, 힘이 약하면 양자화 계단을 넘는 프레임이 적고
**갱신율이 실제보다 낮게 측정된다.** 같은 센서로 접촉 강도만 다른 두 run 을 비교:

| run | 최대 \|F\| | 접촉구간(\|F\|≥1N) 갱신율 | 변화 프레임 | 무반응 채널 |
|---|---|---|---|---|
| `005724` (약접촉) | 3.2N | 27.0Hz | 29% | 3/12 (finger3 전멸) |
| **`010320` (양호)** | **5.3N** | **72.6Hz** | **81%** | **0/12** |

**교훈**: 접촉이 확실할 때만 갱신율이 **센서 상한(83.3Hz)** 에 근접한다. 약접촉에서 나온 낮은 값은
**센서 성능이 아니라 측정 하한**이다. → 촉각 갱신율은 **반드시 접촉 상태에서** 판정할 것.

(부수 효과: `005724` 에서 무반응이던 finger3 는 고장이 아니라 **미접촉**이었음이 확인됐다 —
`010320` 에서 2052회 변화 / 최대 1.6N.)

## 5.5 검토 — 데이터시트 83.3Hz 와 발행률 설계

### Q1. 데이터시트 83.3Hz 는 "최소 보장값"인가?

**아니다 — 실측은 83.3Hz 가 실제 스트리밍 주기라는 쪽을 지지한다.** 근거:

| 관측 | 값 | 해석 |
|---|---|---|
| 발행 tick | 11.12ms (89.94Hz) | 퍼블리셔 **고정 타이머**(`tactile_hz=90`) |
| 변화간격 중앙값 | 11.14ms | = 1 tick. **타이머를 재고 있을 뿐 센서 rate 가 아님** |
| 변화간격 분포 | 1 tick 84.1% / 2 tick 11.1% / 3+ 4.5% | 센서가 발행보다 **느려서** 생기는 빈 tick |
| 접촉구간 변화율 | **72.6Hz** = 83.3Hz의 **87%** | 나머지 13% 는 0.1N 양자화로 값이 안 바뀐 프레임 |

**결정적 논거**: 퍼블리셔가 89.94Hz 로 도는데 값이 바뀌는 tick 이 84.1% 뿐이다.
만약 센서가 90Hz 이상이면 거의 **모든** tick 에 새 프레임이 있어야 하고 변화율도 89.9Hz 에
근접해야 한다. 관측(72.6Hz, 84.1%)은 **센서 < 발행률**임을 뜻한다 ⇒ 83.3Hz 와 일관.
클럭 비트로 예상되는 중복률 `1 − 83.3/89.94 = 7.4%` 도 관측된 2-tick 갭(11.1%)과 부합한다.

> **단정할 수 없는 부분**: 이 방법의 상한은 발행률(89.9Hz)이므로 "83.3Hz 초과 ~90Hz 미만"은
> 배제하지 못한다. 확정하려면 **SHM `Paxini_seq` 증가 횟수/초** 를 제어 PC 에서 세야 한다
> (writer 가 프레임마다 +1 하지만 토픽에 노출되지 않음).
> 참고로 83.3Hz = **정확히 1/12.0ms** 라, 하한이 아니라 **고정 프레임 주기** 설계로 보인다.

### Q2. 촉각 발행률도 다른 토픽처럼 200Hz 로 올려야 하나?

**권장하지 않는다.** 관절과 촉각은 **소스 rate 가 근본적으로 다르다.**

| | 소스 rate | 200Hz 발행 시 | 새 정보 |
|---|---|---|---|
| 관절 (`arm_hz=200`) | **1kHz** | 매 tick 새 데이터 | ✅ 200Hz 전부 유효 |
| 촉각 (`tactile_hz=90`) | **83.3Hz** | `1 − 83.3/200` = **58% 가 순수 중복** | ❌ 여전히 83.3Hz |

즉 현재 설정(`arm_hz=200` vs `tactile_hz=90`)의 비대칭은 **버그가 아니라 각 소스 rate 에 맞춘
올바른 설계**다. 200Hz 로 올려도 **정보량은 1Hz 도 늘지 않고**, 대신:

- 브리지 콜백(`_on_ft`) 호출이 **2.2배** 증가 → §F2 가 지적한 **GIL 경합**(ROS executor 스레드 ↔
  모션 루프)을 악화시킬 수 있다. 지금 루프 97.8Hz 가 정상인데 굳이 리스크를 만들 이유가 없다.
- 얻는 것은 sample-and-hold 지연 **11.1ms → 5ms** 뿐이고, 배포 루프 주기(10ms)와 같은 수준이라
  체감 이득이 작다.

**대신 권장 (효과 순)**

1. **`Paxini_seq`(또는 센서 timestamp)를 토픽에 노출** — 런타임 비용 0. 소비자가 새 프레임/
   스테일을 구분할 수 있고, **진짜 센서 rate 측정이 가능**해진다(§6-1 한계 해소). 이번 계측에서
   가장 아쉬웠던 부분이다.
2. **이벤트 구동 발행** — `Paxini_seq` 가 바뀔 때만 발행. 중복 0%, 지연 최소, 정확히 83.3Hz.
3. 타이머를 유지하려면 **~100–120Hz** 가 상한으로 합리적(83.3Hz 대비 약간의 여유).
   **200Hz 는 83.3Hz 소스에 대해 기술적 근거가 없다.**

## 5.7 값 변화 간격 분포 — 최소 / 평균 / 최대

tick 이 아니라 **실제 값이 바뀐 시각들 사이의 간격**으로 낸 통계
(`tools/analyze_change_rate.py`, run `20260727_010320_kiwi_contact`).

| 토픽 | 구간 | 변화횟수 | **평균 rate** | robust 범위(사분위) | 1초창 최소~최대 | 평균 간격 |
|---|---|---|---|---|---|---|
| `/paxini/right/ft` | 전체 67.5s | 3118 | **46.19Hz** | 88.3~90.3Hz | 0~89Hz | 18.56ms |
| 〃 | 활성(80%) 54.1s | 3118 | **57.60Hz** | 88.3~90.3Hz | — | 16.51ms |
| 〃 | **부하(\|F\|≥1N) 39.5s** | 2868 | **72.63Hz** | 88.9~90.3Hz | 0~88Hz | 13.78ms |
| `/hand/right/joint_states` | 전체 67.5s | 10825 | **160.36Hz** | 188.2~201.5Hz | 82~163Hz | 6.24ms |
| `/franka/right/joint_states` | 전체 67.5s | 74 | **1.10Hz** | 20.0~200.3Hz | 0~23Hz | 336.31ms |
| 〃 | 활성(10%) 7.0s | 74 | **10.50Hz** | 99.7~200.3Hz | — | 52.91ms |
| `/hand/right/kin` | — | **0** | **0Hz (FROZEN)** | — | — | — |

**간격 분포 상세** (촉각, 부하 구간): 최소 7.19 / 25% 11.08 / 중앙 **11.14** /
평균 **13.78** / 75% 11.25 / 최대 111.09 ms

### 이 표를 읽는 법 (중요)

- **평균 rate = 변화횟수/시간** 이 유일하게 신뢰할 수 있는 대표값이다.
- **robust 범위(88.9~90.3Hz)** 는 "바뀔 때는 tick 간격으로 바뀐다"는 뜻이다. 사분위가 전부
  1 tick(11.1ms)에 몰려 있기 때문이며, **센서가 90Hz 라는 뜻이 아니다.**
  평균(13.78ms)이 중앙값(11.14ms)보다 큰 것이 핵심 — **2 tick 이상 벌어지는 갭이 섞여 있어서**
  평균 rate 가 72.6Hz 로 내려간다. 이 갭이 곧 "센서에 새 프레임이 없던 tick" 이다.
- **1초창 최소~최대** 는 시간에 따른 실제 변동폭이다. 촉각 0~88Hz 의 `0` 은 무접촉 구간,
  `88` 은 강접촉 순간이다.
- **개별 간격 극단값은 쓰지 않는다.** 최소 간격이 tick(11.12ms)보다 짧은 7.19ms 로 나오는데,
  이는 센서가 빨라진 게 아니라 **DDS 도착 지터**다(1/7.19ms = 139Hz 는 물리적으로 불가능).

### 채널별 (촉각 12ch, 전체 구간)

| finger | 채널 | 변화횟수 | 평균 rate | 평균 간격 |
|---|---|---|---|---|
| thumb | ch0 / ch1 / ch2 | 968 / 1119 / 758 | 14.3 / 16.6 / 11.2Hz | 46.6 / 40.3 / 59.5ms |
| finger1 | ch3 / ch4 / ch5 | 586 / 281 / 396 | 8.7 / 4.2 / 5.9Hz | 76.7 / 160.2 / 113.6ms |
| finger2 | ch6 / ch7 / ch8 | 674 / 806 / 640 | 10.0 / 11.9 / 9.5Hz | 67.7 / 54.8 / 90.5ms |
| finger3 | ch9 / ch10 / ch11 | 613 / 753 / 686 | 9.1 / 11.2 / 10.2Hz | 73.4 / 59.6 / 65.6ms |

**개별 채널은 4~17Hz** 로만 바뀐다. 12채널 중 하나라도 바뀌면 프레임이 바뀌므로 합산이 72.6Hz 가
되는 구조다. 즉 **0.1N 양자화 때문에 채널 단위로는 훨씬 드물게 갱신**된다 —
힘이 큰 thumb(ch0-2)이 가장 자주 바뀌고, 접촉이 약한 finger1(ch4 = 4.2Hz)이 가장 드물다.

> **결론**: 촉각의 실효 갱신율은 **접촉 시 72.6Hz**(무접촉 포함 전체 평균 46.2Hz)이며,
> 센서 상한 83.3Hz 의 87% 다. 추론이 쓰는 9.8Hz 대비 **7.4배 여유**로, 여전히 병목이 아니다.

## 6. 측정의 한계 (신뢰도 명시)

1. **값 변화율 ≤ 토픽 발행률** — 원리적 상한이다. 소스가 발행률보다 빨라도 볼 수 없으므로,
   실측값은 **하한(lower bound)** 으로 읽어야 한다.
2. **이 워크스페이스에서는 원 소스를 직접 측정할 수 없다.** 제어 스택(EtherCAT·RT·
   `shm_state_publisher`)은 **다른 PC** 에서 돌고, SHM(key `0x7951`)이 이 머신에 없어
   (`ipcs -m` 확인) DDS 토픽만 받는다. 따라서 §3 의 "원 소스 rate" 는 **코드 근거**이며 실측이 아니다.
3. **관절은 실제로 5배 다운샘플되고 있다** (1kHz → 200Hz). 단 배포 루프가 97.8Hz 로 소비하므로
   **현재 파이프라인에는 영향 없다**(200Hz ≫ 97.8Hz). 1kHz 원본이 필요해지면 SHM 직접 접근이
   필요하다.
4. 촉각은 **센서 83.3Hz vs 발행 타이머 89.9Hz** 의 독립 클럭 조합이라 구조적으로 ~7.4% 중복이
   생긴다(빈 tick 재발행). 또 writer 는 지연을 줄이려 **버스트 시 최신 프레임만 유지**하므로
   그 경우 이전 프레임은 버려진다.

## 7. 결론 및 다음 단계

**rate 관련 항목은 전부 정상으로 종결한다.**

| 항목 | 결론 |
|---|---|
| 루프 rate | ✅ 97.8Hz — 학습 100Hz 정합. §F4 `#1`(FACTOR 정합)·`#2`(루프 경량화) **불필요** |
| 센서 갱신 | ✅ 촉각 83.3Hz(관측 72.6Hz) · 손 관절 199Hz — 추론 9.8Hz 대비 충분 |
| 모션 끊김 | ✅ `q_target` 중앙값 98Hz — §C1(QoS) 해결 상태 유지 |
| **힘 크기** | ❌ **thumb 4.8N vs 임계 10N (45–52%)** ← **유일한 남은 문제** |

**다음 단계 — 힘 경로 (§F7 로 이관)**  → 실행 항목은 **[부록 C 재테스트 체크리스트](#부록-c--재테스트-체크리스트-다음에-할-것)** 에 정리했다.

힘 문제의 원인 후보는 [TROUBLESHOOTING §F7](TROUBLESHOOTING.md) 에서 더 좁혀졌다:
**P2P 수집 → ROS2 배포로 바뀐 힘 측정 경로.** 추론이 쓰는 합 연산은 양쪽 동일한데
*무엇을 합하는지*가 다르다 — 학습/수집은 **127점 tactile 합(Σ127)**, ROS2 배포는 브리지가
`/paxini/*/ft`(4×3)를 point0 에 실어 합하므로 **결과가 곧 `ft`** 다. 두 값이 같을 조건은
`ft == Σ127` 하나뿐이므로, **1회 실측으로 H1(측정 경로) / H2(모션)이 갈린다.**

1. **`ft` vs `Σ127` 실측** — `deploy_ros2_exp_ftcheck.py` / `deploy_ros2_exp_rawft.py` (§F7).
   H1 이면 브리지가 `/paxini/right/raw`(127점)를 구독하도록 고치는 것이 해결책이다.
2. 이번 rate 계측이 여기에 기여하는 것: `sensor_update_rate.py` 로 **두 토픽을 동시에** 잡아
   갱신율·값 범위를 나란히 비교할 수 있다.
   ```bash
   python3 tools/sensor_update_rate.py --duration 30 \
       --topics /paxini/right/ft /paxini/right/raw --out docs/rate_log/ft_vs_raw
   ```
   ⚠ 본 문서 §2 에서 `/paxini/right/raw` 가 **전 채널 0** 이었다고 적은 것은 **writer 미실행
   시점의 측정**이다. writer 가 살아있는 상태에서 **반드시 재측정**해야 H1 판정에 쓸 수 있다.
3. 참고: 이번 tomato 실측 4.5–5.2N 은 2026-07-14 baseline(3.2–3.7N)보다 **개선**되었다.
4. 힘-도달 curl 실험(§F5 `#2`)을 하려면 `deploy_ros2_exp_forcecurl.py` 의 **import 순서 버그**를
   먼저 고쳐야 한다(구 추론 엔진이 로드되어 baseline 과 비교 불가 — 미수정 상태).

### C.0 재테스트가 **불필요**한 항목 (확정됨)

| 항목 | 결론 | 근거 |
|---|---|---|

### C.1 코드로 이미 확정된 것 (측정 불필요)

1. **`ft` 는 Σ127 이 아니다** — `decoded_to_numpy_arrays` 가 UART 프레임의 **서로 다른 필드**
   (`decoded["ft"]` / `decoded["tactile"]`)에서 각각 채운다. `ft` 는 센서의 자체 FT 블록이며
   127점 합으로 계산되지 않는다 ⇒ **D2 의 "ft ≡ Σ127" 가정은 코드 근거가 없다 → H1 성립 가능.**
2. **단위 불일치는 아니다** — `FT_SCALE = 0.1`, `TACTILE_SCALE = 0.1` (둘 다 "0.1 N units" → N).
   따라서 `ft ≪ Σ127` 이 나오면 **스케일 실수가 아니라 물리적으로 다른 양**이라는 뜻이다.
   (측정된 `/ft` 의 0.1N 양자화도 `FT_SCALE=0.1` 로 정확히 설명된다.)

### C.2 ★ 최우선 — `ft` vs `Σ127` 실측 (H1/H2 판별)

**비용 0 안 먼저**: `paxini_writer` 터미널 스크롤백을 확인한다. writer 는 이미 Σ127 을 찍는다 —
`res = np.nan_to_num(arrays["tactile"]).sum(axis=1)` (기본 2초 주기). 01:03 run 때 터미널이
아직 열려 있으면 **새 측정 없이 판별 가능**하다.

터미널이 닫혔다면 (로봇 모션 불필요 — **손으로 손가락을 눌러도 판별된다**):
